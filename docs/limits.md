# Known limits

- The default shell requires Linux x86_64 with bubblewrap 0.9+ and usable user namespaces. Unsupported hosts must explicitly choose --no-sandbox; namespace policy never silently falls back.
- Model text streams with `--stream` in `molt do` and by default in the TUI (`/stream off` disables it); thinking is not shown and tool calls wait for the complete message. Preview delivery is best effort, and the final reply remains complete.
- A project's `.molt/config.toml` takes `check`, `ask_paths` and `instruction_files` only: no project `suite` or command directory yet (commands stay in `.molt/commands`). The file is part of the workspace, so a result can change it like any file; confirm mode does not stop for it unless `ask_paths` names `.molt/`. Configs are re-read only when the interface starts.
- The audit log records every message, file contents and model conversations included, and is never rotated; it grows with every run in a data dir.
- Audit startup, verification and nonempty tail reads still scan the whole log, but memory is bounded by one record plus the requested tail. A record is limited to 16 MiB including its newline; oversized, malformed or unterminated records are refused, including on restart. The writer stops before persisting an oversized entry. `tail -n 0` opens the file without scanning; `read_all` intentionally retains every returned entry. Tail validates record syntax throughout the file, but only verification and startup check the hash chain.
- Reading one trace back from the audit log scans the log from the start: there is no index yet. One read looks through at most 256 MiB and keeps to its deadline, and two run at once.
- `molt runs` ([runs.md](runs.md)) says where a result went as its run's reply did: a result kept in its fork and applied later (from the interface, `molt apply` or `result.apply`) is still listed as `kept`, and a `--commit` is not shown. What an interrupted run spent is known only when the planner still answered; a run whose planner was killed shows `?`. Sessions group runs only: a session cannot be resumed, and the interface starts a new one each time it opens even when it picks up the last one's conversation.
- The kernel drops a message nested more than 100 levels deep, so every logged message can be read back.
- Only Cargo's cache is mounted for you (by the `rust` profile, or `--deps-cache cargo`); Go, Node and Python dependencies must be in the project (vendor, `node_modules`, `.venv`) or mounted with a policy. The preflight before a run is a file check, not a build; `molt env doctor` runs the profiles' probes, but not before every run. No profile opens the network only to package registries: commands have all of it (a user profile or policy with `network`) or none. A user profile replaces the built-in profile of its name whole; a project's `.molt/config.toml` cannot define profiles. With the Cargo cache, crates missing from it cannot be fetched, sources Cargo extracts privately are writable by later commands of the same workspace (as its build directory is), and local-registry or directory sources named in the host Cargo config are not mounted. `molt sandbox suggest`, a generated policy draft, is not built yet.
- The private build directories (`<data dir>/work/.molt/build`) are never cleaned up, and each Cargo slot a workspace used holds a full build; delete the directory to reclaim the space. A result's build artifacts are recognized by name and content, not by which command made them: a compiled file or a file under a top-level `target-*/` that an attempt makes with a command, rather than with its file tools, is left out too.
- Background processes ([tools.md](tools.md#background-processes)) talk through pipes, not a terminal: a program that needs one (a full-screen editor, a password prompt) does not work, and one that buffers its output off a terminal shows it late. Without the network, each `run` command and each process has a network of its own, so a command cannot reach a process's ports; run the server and the client in one process. A process does not survive a restart of the shell service or of Molt, and a planner that dies leaves its processes until their 30 minutes end or the shell service stops. They are off by default (`MOLT_PROCESSES=on`), and `molt` has no flag for them yet.
- Git history ([tools.md](tools.md#git-history)) is read-only and off by default (`MOLT_GIT=on`, no `molt` flag yet). It reads committed history and compares files by content, so a file whose only difference is a clean filter or line-ending conversion (Git LFS, `eol=crlf`) shows as changed, and staged and unstaged changes are not told apart. Submodules are named but not entered; a partial clone's missing objects are not fetched. An answer is at most 40 KiB, a log at most 100 commits, a query at most 30 s; `blame` reads a commit, not the attempt's current file, and there is no query for a whole old file yet.
- What an interrupted task in the interface spent comes from its progress events, which are best effort: a call whose events were lost is missing from the session total, and the stopped run's audit log is not read back to settle it. `r` after a stop does not take what the stopped attempts spent off the new run's budget.
- After an interrupted run, forks are removed only from a scratch dir inside the data dir (the default); a configured scratch elsewhere may be shared with other runs and is left alone. A `molt do` killed outright (SIGKILL) removes none. A run with `--checkpoint` that stops keeps its forks for `molt resume`. An interface (`molt`) that crashes or is killed removes no fork its session made: the one a result waited in is picked up as a kept result, and others stay in the scratch dir until removed by hand.
- The check's designer is only told not to do the task, and told afterwards when it changed files beyond its check files: nothing stops it from spending its share of the budget that way. When its share runs out without a check, the run stops rather than falling back to a rubric, since a designer that submitted none has none to fall back to. `--criterion` gives criteria without commands; only a designed rubric can have criteria a command decides.
- A rubric's model-judged criteria are a model's reading, not a proof: the judge can be wrong, and nothing but the criteria with a command checks the result. In the interface, a constraint that adds a check is refused while a run is being judged by a rubric.
- Only `molt do --commit`, `molt resume --commit` and the interface's `/commit on` commit a result, always on the current branch (`--branch` is for `molt do` only). `molt undo` takes back only those commits, and refuses a file changed after the run rather than merging the revert into it (use `git revert` then).
- A checkpoint is saved whole at each boundary, so a long conversation makes each save bigger. An attempt that left turns out also saves their full text, up to 1 MiB. The interface's task queue lives in memory: normal exit prints unexecuted tasks, while a crash loses them.
- Promotion updates the registry pointer but does not yet restart the running service; hot swap with in-flight draining lands with milestone 6.
- Call-cycle checks at the gate remain future work.
- Default recall matches keywords with stemming, so differently worded notes can be missed. Chinese, Japanese and Korean match on pairs of characters, so a query can also find a note where its pair spans two words, and a one-character query word finds only notes where that character stands alone. Optional offline word-vector recall needs a reviewed hash-pinned local model; its mean-pooling backend does not understand word order or supply a pretrained vocabulary.
- Notes learned from a run stay with that project, preferences included: a run's record holds text the project's files and commands chose. Only notes you write or promote yourself are shared between projects. Clones of one project share its data dir, so molt runs in one of them at a time.
- The project model indexes the first 20,000 source files of a project, in walk order; `memory.index` reports when a project has more. A file that takes more than 2 seconds to parse keeps the symbols found by then.
- Directory instruction files ([do.md](do.md#project-instructions)) reach an attempt through its `read_file`, `list_files`, `search`, `write_file` and `edit_file` calls only: a `run` command that changes files in a directory the attempt has not reached is not held back, and a `tool.before` hook that moves a write to another path is not looked at again. The designer, the reviewer and an explorer get none of them.
- Legacy `topic:<name>` capabilities still permit both publication and subscription; use the explicit rights to reduce them. Events already accepted for delivery may arrive after revocation.
- Model prices are as current as the last `molt prices update` (or the release's snapshot) and as right as the community list they came from; a price that changes mid-run is not picked up until the next run. Models that LiteLLM lists only with tiered or regional prices, such as some Qwen models, have no price until declared in `MOLT_MODEL_PRICES`.
- The OpenAI Responses adapter ([providers-and-prices.md](providers-and-prices.md#openai-responses)) handles text and function tools only, always without server-side state (`store: false`): no `previous_response_id`, built-in tools, media or background responses. Function call and message item ids are not sent back, only reasoning items' ids; a reasoning item without encrypted content is left out of later calls. The planner learns a declared context window from the first reply, so that first call is fitted to its guess or `MOLT_CONTEXT_TOKENS`. It has been checked against a scripted endpoint only, not a live model.
- Chat Completions reasoning ([providers-and-prices.md](providers-and-prices.md#reasoning-on-chat-completions)) is told apart by turn only: it goes back with every assistant message after the last user message that holds no tool result, and is left out before it, whatever the endpoint. An endpoint that wants the reasoning of earlier turns too, or none at all, is not given a setting for it. It has been checked against a scripted DeepSeek-format endpoint only, not a live model.
- Workflows (`docs/rfc/0001-workflows.md`) have three built-ins, `verify`, `quick` and `ask`; other workflows come only from the planner's own `Config`, not from a file. The learn stage runs on the caller's side, which knows only the built-ins: a workflow from the planner's configuration learns as the caller asks. The interface does not show the verification level yet. `quick` holds back any diff the fixed rules question, whatever its size; it does not send a large diff to the reviewer model. How long `ask` and `quick` take against a real model has not been measured yet. `/continue` follows only the last task of the interface's conversation; `molt do` has no way to go on from a run.
- `explore`'s sub-agent (see [explore.md](explore.md)) cannot run commands, since nothing yet runs one that provably leaves the fork as it was; the `explore` calls of one turn run one after another; its turns are not streamed to the interface. How many tokens it saves per task has not been measured.
- The web service has no search: an attempt reads known URLs or links from pages it read, without running scripts. It does not use an HTTP proxy; an explicit public-IP DNS JSON resolver supports fake-IP DNS but still needs a route to that resolver and the public page addresses. Startup DNS probes sample at most 16 hosts, using wildcard apexes; every actual fetch validates its own destination.
- Extension packs ([extensions.md](extensions.md)) install from a local directory, a `.tar`, `.tar.gz` or `.tgz` archive, or one commit of a git repository over https or ssh, also by name from a registry you added (unsigned, its index fetched again at each lookup), and bring MCP servers, services, hooks, skills and commands only: not environment profiles, roles, prompts or workflows. A pack's service runs only as a candidate in the Linux sandbox, without the network, so a pack with one does not start where the sandbox is unavailable or on the NATS transport; its tools are offered under the names it gives them, and two packs, or a pack and a service of yours, with a tool of the same name are refused. Their hooks cannot use files of the pack. Approval is of the grant's lines, so a server's `calls` lowered by an update is still asked about. A Claude Code plugin's agents are not imported, nor its hooks on events Molt has none of, of a `prompt` type, on MCP tools, or whose command is more than one script or whose script needs files beside it; an imported hook is told nothing of a Claude Code session. Its servers get no network, and its commands lose `allowed-tools` and `model`. A pack from git is refused when its tree has a submodule or a symlink, and its LFS files arrive as their pointers; the fetch runs git with a scrubbed environment and configuration, not in a sandbox, within 120 s and 128 MiB, and a private repository is reached only through ssh keys or `~/.netrc`, not a credential helper. Removing a pack leaves the tool lists its servers cached, and its services' private state, in a data dir chosen with `--data-dir` unless that dir is named to `molt ext remove`.

- What a long attempt keeps of its left-out turns ([do.md](do.md#long-tasks)) is its own conversation's: `earlier_result` cannot read another attempt's turns, a designer's, or an explorer's, and only attempts get notes from the `compactor`. Whether a file changed since a read is told for `read_file` alone; a `search` or `list_files` read back may be out of date without saying so, and a command may have changed files the record does not list as changed. How much `MOLT_COMPACT=model` changes completion, repeated exploration, cost and time on long tasks has not been measured: no benchmark compares it with the record alone yet.
### Cancellation and model settlement

Dropping an SDK `PendingReply` requests `kernel.cancel` for that request. The kernel verifies the original caller, sends a kernel-only control message, and keeps the request open for one final cleanup or settlement reply. Cancellation is idempotent and does not affect another request. SDK services can use `serve_cancellable` for cleanup; ordinary concurrent handlers stop locally on cancellation. Cancelled queued work does not start.

Link loss ends concurrent admission immediately, even if every slot is occupied. Cooperative handlers get up to two seconds to clean up before they are aborted; queued work does not start after disconnection. Dropping a server cancels and removes its active request registrations. Shell shutdown closes command admission before sending TERM, and dropped shell request futures also abort their output readers.

Dropping the SDK service itself closes every pending call's waiter and requests cancellation without awaiting a reply. Background cancellation after a drop is best effort and bounded to one second, so a stalled transport cannot retain the link forever. Remote cancellation and unsettled usage remain unconfirmed.

The adaptive schedule ([do.md](do.md#adaptive-schedule)) has not been compared with the fixed one on the benchmark yet: whether it is cheaper or as successful is not known. It estimates what a new attempt costs from what this run's attempts cost, since the planner has no price list, so an escalation to a pricier model can cost more than it assumed. It decides between attempts, not inside one: an attempt is never stopped for another approach, only joined by another. It stops starting attempts while any call's cost is unknown, so a resumed run with calls left unanswered does not escalate.

The planner gives each attempt its own cancellation token. A winner stops competing attempts; budget exhaustion or unknown model cost stops new actions throughout the run. The one exception is a call cancelled because its attempt was stopped while the run went on, such as one that lost the race: its cost is unknown too, and is reported in `uncounted_calls`, but it does not stop the winner's review and apply, so a run can pass its budget by up to one call for each attempt it stopped. Shell cancellation and timeout send TERM to the process group, allow 500 ms for cleanup, then send KILL and reap the leader before replying. Service shutdown uses the same grace. Process groups alone cannot contain a program that deliberately creates a new session; OS isolation is tracked by #9. A cancelled run drops its attempts' forks, unless the request sets `keep_cancelled_forks`: then it leaves them for the caller to keep or drop, as the interface does to keep an interrupted task's work.

The gateway closes its local HTTP request on cancellation and audits a correlated settlement record with `local_stopped`, `remote_cancel_confirmed`, `usage` and `cost_usd`. Anthropic Messages has no remote cancellation acknowledgement here, so remote cancellation and missing usage remain unknown. A completion already received wins the race and is counted once. After a kernel timeout, one authenticated late model reply can still be audited for up to one hour, without delivering a second run result; the late-settlement registry is bounded and temporary, while accepted records persist in the audit log. `molt audit --help` describes querying the log.

Run `cost_usd` is the known subtotal. `uncounted_calls` now includes pending calls, errors without usage, and replies without a known price. The terminal explicitly labels the known cost and incomplete settlement; automatic memory learning is skipped when settlement is incomplete. This is an estimated spending limit, not a provider-enforced dollar ceiling.

`planner.design` uses the same settlement rule, including failed and cancelled
designs. A missing or incomplete canonical usage record is refused before
serde defaults can turn it into zero tokens. `DesignResponse.cost_usd` is a
known subtotal; `uncounted_calls` marks the unknown part. Its optional `error`
reports a failed design while preserving settlement, and `cancelled` means
local work stopped, without claiming the provider stopped billing. Invalid
requests still return protocol errors. Consumers must inspect `error` and
`cancelled` before treating a missing command as an unverified task.

With complete settlement, `remaining_budget_usd` carries the task's effective
limit minus the design cost, including the planner's configured default. The
TUI forwards exactly that remainder to attempts, shows incomplete costs on
the confirmation screen and session total, and starts no attempts when design
cost is unknown or the remainder is exhausted. The new fields have serde
defaults for reading older replies; older consumers should be updated to
handle failed design replies explicitly and honor the remaining limit.
- `molt serve` ([serve.md](serve.md)) serves one workspace and one session at a time, on a Unix socket or a pipe only, and clients cannot share a session. Its progress events name a tool call in one line and do not carry the call's result or an attempt's diff as it goes; ask `result.diff` for that. No JSON Schema or client library is generated from the protocol's types yet, and the interface always starts a server of its own rather than attaching to a running one.
- `molt acp` ([acp.md](acp.md)) speaks ACP version 1 and has not been tried in an editor by hand yet, only with a scripted one. An attempt's question can be answered with one of its options or "let it decide", not with text of your own: ACP version 1 has no way to ask for text. It does not load past sessions, use the editor's files, terminal or MCP servers, offer modes or a model picker, or commit results (`[tui] commit`); a prompt takes text and files, not images. One task runs in a folder at a time, across the editor's threads. It is not in the ACP registry yet.
- Models ([models.md](models.md)): a named endpoint serves only the models declared for it, and its key comes from an environment variable: there are no keyless endpoints and no key files. `molt models` reads the user config of the default setup, not a `--config` file. The gateway answers `output_schema` through a tool only on the Anthropic protocol; on the OpenAI one, a model found to ignore it is refused a schema. The planner fits a conversation to the run's model's context window, also for a role routed to another model.
- Candidate services ([services.md](services.md)) have one backend, the Linux x86_64 sandbox, on the Unix transport only: no Wasm backend, nothing on macOS, other architectures or NATS, where a candidate does not start. A candidate gets no network and no host path but its program and its state directory; there is no setting for more mounts or a network allowlist yet. Only `echo` in the example configuration runs as a candidate: `fs`, `memory`, `planner` and the other built-in services still run natively, so no gate can promote them. There is no automatic gate or evaluator yet, and its resource limits are per process, not a quota on its state directory.
- `molt improve` ([improve.md](improve.md)) has the only automatic gate, for the planner's prompts that do not guard acceptance, not for services (the improver is the other candidate besides `echo`); it has been tested end to end with a fake model only, proposes one candidate per cycle, and compares pass counts and costs without a significance test.
