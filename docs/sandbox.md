# Linux command isolation

The read-only system runtime includes `/etc/alternatives` so distribution-provided links such as `/usr/bin/cc` and `/usr/bin/awk` resolve to their tools. Other host `/etc` contents are absent except the loader cache, certificate directory and, when networking is enabled, resolver configuration.

The default `molt do` shell and done-check use the same Linux x86_64 backend, requiring `/usr/bin/bwrap` (bubblewrap 0.9+) and working unprivileged user namespaces. Startup probes the backend and fails if required capabilities are missing. `molt do --no-sandbox` and `molt-tools shell --no-sandbox` are explicit host choices; the library equivalent is `Shell::with_policy(..., ExecutionPolicy::Unconfined)`. Other architectures and macOS currently need that explicit choice.

Each command starts from an empty mount namespace with read-only system runtime paths, a read-only original project, its writable `fs.fork` directory, private tmp/home, and isolated PID, user, IPC, UTS and network namespaces. Direct isolated shell calls on the original project are refused. Ignored entries linked back to the project remain read-only; shared build directories are not writable. Build output goes to a private writable directory instead: every command gets `CARGO_TARGET_DIR` and `GOCACHE` under `<scratch>/.molt/build/<key>` (`<data dir>/work/.molt/build` by default), keyed by the original workspace and kept across its forks and runs, and `PYTHONDONTWRITEBYTECODE=1`. Cargo's directory is one of several slots, each used by one command at a time, so parallel attempts never replace each other's binaries; Go's cache is shared. Only those directories are mounted, writable at their own paths. A variable passed with `--pass-env` or a policy's `environment` takes precedence. With `--no-sandbox` commands get the same variables, unless the service's own environment already sets them. `/proc` shows only sandbox processes. User namespaces cannot be nested, capabilities are dropped, and a seccomp filter blocks creating AF_UNIX sockets (so no host service socket is reachable through a mounted path or, with host networking, an abstract name) and AF_UNIX datagram socket pairs (which could send to such sockets by address), io_uring (which could bypass syscall socket filtering), and alternate syscall ABIs. Programs must use ordinary file/socket I/O rather than requiring io_uring. The default denies network access. With explicit host networking enabled, IP connections, including localhost, are allowed; AF_UNIX stays denied. Stream and seqpacket socket pairs, which reach only each other, are allowed: Rust's standard library and Node's libuv start child processes with them, so `cargo test` and `node --test` need them.

`molt do --sandbox-policy /trusted/path/policy.json` supplies a JSON policy. It must be owned by the current user, not writable by others, and outside the canonical project and scratch roots. Each canonical path component is opened without following replacement symlinks; file permissions and content are checked through the same descriptor, and reads are bounded to 64 KiB. The shell reads it at startup; no request payload or repository file selects a policy. The default shell service is protected from service-driven replacement. A custom service configuration is still an explicit trusted user choice, and custom shell implementations are responsible for their own isolation.

```json
{
  "network": false,
  "read_only": ["/opt/toolchains", "/opt/dependency-cache"],
  "environment": ["RUSTUP_HOME", "CARGO_HOME"],
  "memory_mb": 4096,
  "cpu_secs": 600,
  "file_mb": 128,
  "open_files": 256,
  "processes": 2048
}
```

Dependencies mount at their canonical absolute paths. `--pass-env NAME` explicitly allows another variable; HOME always points to private `/home/molt`, and service bus / Anthropic credentials cannot be passed. The environment profiles below mount the toolchains a project uses; other paths outside `/usr` need declared read-only mounts. `"set_env": {"NAME": "value"}` sets a variable for commands, over the passed ones, with `$WORKSPACE`, `$BUILD` and `$PATH` replaced as in a profile. Build output already goes to the private build directory above; a dependency cache that normally lives in a host directory must be put in private `/tmp`. For example, declare a Rust toolchain mount and RUSTUP_HOME, set CARGO_HOME to a private `/tmp` location, and explicitly enable network when downloading dependencies; for offline builds from the Cargo cache you already have, use `--deps-cache cargo` (below). A cache in private `/tmp` disappears after each command. A C build using system `cc` needs no extra mounts.

### Environment profiles

What a toolchain's commands need from the sandbox is an environment profile: data, not code. Molt has five built in (`crates/molt-tools/src/env_profiles.toml`), and each applies to a project that has one of its files:

| Profile | Applies with | Gives commands |
| --- | --- | --- |
| `rust` | `Cargo.toml` | the installation of `cargo` and `rustc` found on PATH (for rustup's proxies, their `bin` directory and rustup's home, with `RUSTUP_HOME`; never the rest of the Cargo home), and builds offline from your Cargo cache when it has one, as `--deps-cache cargo` does |
| `python` | `pyproject.toml`, `setup.py` or `requirements.txt` | the installation of `python3` |
| `python-venv` | `.venv/pyvenv.cfg` | `VIRTUAL_ENV` set to the workspace's `.venv`, and its `bin` first on `PATH`, so `pytest` and `python -m pytest` find what is installed there |
| `go` | `go.mod` | the installation of `go` and `gofmt`, `GOTOOLCHAIN=local` and `GOPROXY=off`, so a missing module fails at once |
| `node` | `package.json` | the installation of `node`, `npm` and `npx` |

A tool in the system directories needs no mount. Otherwise the prefix above its `bin` directory is mounted read-only (`/opt/node22` for `/opt/node22/bin/node`), or only the `bin` directory when that prefix is the home directory or one directly in it (`~/.local`, `~/.cargo`); nothing that holds or is inside the project or the scratch directory is mounted. Build output still goes to the private build directory above. Every profile leaves the network off. What a profile cannot provide (a tool not on PATH, no Cargo cache) is logged by the shell service, and the run goes on without it.

A project only picks which profiles apply, by having their files: what is mounted, set or opened comes from Molt or from you, never from a path the project names. So `.venv`'s own `pyvenv.cfg` is not followed to mount its base interpreter; a `.venv` made from a Python outside the system directories needs that Python mounted with a policy. Profiles of your own go in your user config `~/.config/molt/config.toml` (or a `--config` file), as `[environment.NAME]` with the same fields (`detect`, `tools`, `read_only`, `env`, `cargo_cache`, `network`, `probes`), and replace the built-in profile of the same name; `detect = []` turns one off. Only a profile of yours may mount a path you name or set `network = true`. In `env` values, `$WORKSPACE` is the command's workspace (the fork), `$BUILD` the workspace's private build directory and `$PATH` the PATH commands get.

### The readiness check: `molt env doctor`

`molt env doctor [--workspace DIR] [--sandbox-policy FILE] [--pass-env NAME] [--deps-cache cargo] [--build COMMAND] [--fresh] [--json]` checks that a workspace is ready for its commands before any change is made. It runs everything in the sandbox from a fork of the workspace, as a run's commands would, drops the fork after, and calls no model. Each check prints one line with its result, what it found and how long it took, and a one-line fix under each one that fails:

- **Probes.** Which profiles apply, and each one's probes (`cargo tree --offline`, `python -c ...` in the `.venv`, `go list -deps ./...`, `npm ls`), with the line of output that says why one fails, such as `run cargo fetch in the project on this machine` when the Cargo cache lacks the project's crates.
- **Toolchains.** The versions the project declares, compared with the ones commands get: `rust-toolchain.toml` (or `rust-toolchain`) and `rust-version` in `Cargo.toml` against `rustc --version`, `.nvmrc`, `.node-version` and `engines.node` against `node --version`, `.python-version` and `requires-python` against `python3 --version`, and the `go` line of `go.mod` against `go env GOVERSION`. A toolchain rustup does not have is named, with `rustup toolchain install` for it. A range it does not read (`||`, `lts/*`) is not checked rather than guessed.
- **Dependencies.** The file checks of the dependency preflight below, unless commands have network, and whether `molt env prepare` prepared the current `requirements.txt` (below).
- **Variables.** Each one `[readiness] env` lists must be set here and reach commands (`--pass-env`, or set by a profile or the policy). Only whether it is set is looked at, never its value. A model or service credential (`ANTHROPIC_*`, `OPENAI_*`, `MOLT_*`) or `HOME` cannot be listed, since commands are never given them.
- **The build.** `[readiness] build`, or `--build`, is the project's own build command. It runs once the environment checks pass (it is `skipped` when one is blocked), in the sandbox, from the fork, and nothing it writes reaches the workspace.

The verdict is the worst result, and the exit code says which: 0 `ready`, 1 `blocked` (the environment lacks something; fix what is marked blocked), 2 `build_fails` (the environment is ready, and the project's build already fails before any change, so its failures are the project's own, not a run's), 3 `unknown` (a check timed out or was killed). A build that fails for a dependency it could not download is `blocked`, not `build_fails`. `--json` prints the report for CI: the status, each check with its `kind`, `status`, `detail`, `fix` and `ms`, the fingerprint and the total time.

The fingerprint is the SHA-256 of what the environment checks depend on: Molt's version, the profiles that apply, the sandbox policy, the lock and toolchain files (`Cargo.lock`, `package-lock.json`, `yarn.lock`, `go.sum`, `uv.lock`, `rust-toolchain.toml`, `.nvmrc`, `.python-version`, ... and each profile's `detect` files), whether `node_modules`, `vendor` and `.venv` are there and when they last changed, which file each tool on PATH is and when it changed, rustup's installed toolchains, the Cargo cache's directories, `PATH`, and whether each required variable is set. When every environment check passes, the report is kept in the data dir (`readiness/` under it) and an unchanged fingerprint later reuses it (`environment checks cached`); `--fresh` checks again anyway. A blocked or unknown result is never kept, so the check after a fix probes again. The build is never kept: it depends on the project's code, and runs each time.

`[readiness]` goes in your user config, or a `--config` file:

```toml
[readiness]
build = "cargo build --offline"   # the project's build; leave it out to check without one
env = ["DATABASE_URL"]            # variables the project's commands need
before_run = true                 # check before each `molt do`, and when the interface starts
```

A project's `.molt/config.toml` may set `build` and `env` (they are data: the build runs in the sandbox, as the done-check does), and adds to yours; only you can set `before_run`. With `before_run`, `molt do` runs the same check before it plans, from the cache when the fingerprint is unchanged, prints each check that is not ok and the verdict, and does not start, with exit code 1 and no model call, when the environment is blocked. A failing build is printed as the project's own and the run goes on. The interface runs it when it starts and shows the result in its log. Without `before_run`, both keep the cheap file checks below. The check is skipped when commands run unconfined (`--no-sandbox`) or the shell service is not Molt's.

### Dependencies offline

Commands have no network, so a project whose dependencies are not already on disk cannot build in the default sandbox. Before a run starts, `molt do` prints a `dependency preflight:` notice on stderr, and the interface a log line, for each kind it finds missing from cheap file checks: a `Cargo.lock` with registry or git crates (unless the project vendors them through `.cargo/config.toml`, or your Cargo home has a `registry` cache for the `rust` profile), a `go.sum` without `vendor/modules.txt`, a `package.json` with dependencies but no `node_modules`, a `requirements.txt` or `pyproject.toml` dependency list without `.venv`. Each notice says what to do; it is not an error, and the run goes on. It is skipped with `--no-sandbox` or a policy with network. When a sandboxed command without network fails with output that looks like a download failure (`no matching package named`, `crates.io index`, `Could not resolve host`, npm's `ENOTFOUND`, pip's `Failed to establish a new connection`, Go's `dial tcp` and similar), the attempt or designer gets one fixed sentence after the output saying that commands have no network and how the user can provide the dependencies, so it stops retrying downloads.

For Rust, the `rust` profile builds offline from your own Cargo cache whenever your Cargo home has a `registry` directory; `molt do --deps-cache cargo` (also `molt --deps-cache cargo` for the interface, `molt-tools shell --deps-cache cargo`, or `"cargo_cache": "/abs/cargo/home"` in a policy) asks for it outright, and fails to start without one. Run `cargo fetch` (or any build) in the project on the host first. The host's `$CARGO_HOME` (default `~/.cargo`) contributes only `registry/` and, when present, `git/`, mounted read-only at their canonical paths; credentials, binaries and the rest of the Cargo home are never mounted, and passing `CARGO_HOME` as well is refused. Commands get `CARGO_HOME` set to a private writable directory, `<scratch>/.molt/build/<key>/cargo-home`, and `CARGO_NET_OFFLINE=true` (automatic cache cleaning is off, since it would delete from the host cache). Offline, Cargo still writes in its home: its package-cache lock, its last-use database, and the sources it extracts from a downloaded `.crate`. So the private home is an overlay of symlinks, refreshed before each command through descriptors that do not follow symlinks: to the read-only index and `.crate` files, to every source the host already extracted, and to each git database and checkout, with room for Cargo to extract or check out the rest itself from the read-only copies. Source replacement cannot point at the host cache directly, since its layout is neither a local registry nor a vendored directory. Of the host's Cargo config, only `[source.*]` entries and `[registries.*]` index URLs are copied, without URLs that carry a user or password, so a mirror's cache is found under the mirror's name. A crate that is not in the cache fails as it would with `--offline`. The `rust` profile mounts a rustup toolchain for you, as above.


### Preparing dependencies: `molt env prepare`

`molt env prepare [--workspace DIR] [--sandbox-policy FILE] [--json]` gets a Python project's locked dependencies for commands that have no network. Python's pip is the first package manager it supports. The lock is a hash-pinned `requirements.txt`: every line is `name==version` with one or more `--hash=sha256:...`, as `pip-compile --generate-hashes` or `uv pip compile --generate-hashes` writes it. A line that is not pinned or has no hash is refused. So are environment markers, `-r`/`-c`/`-e` lines, and `--index-url`, `--extra-index-url`, `--find-links` or `--trusted-host`, since only your config says where packages come from. The steps are kept apart, each with its own grant:

1. **The environment.** A virtual environment is made in the sandbox with the `python3` on your PATH, in a private directory under the data dir, `deps/python/envs/<key>`. That directory is the only host directory the sandbox may write. The key covers the lock's content, the interpreter, the index and the script grants, so a change in any of them asks for a new environment. The new environment reports which wheel tags it takes.
2. **The download.** Molt itself downloads, never pip: no project code runs while the network is in use. Each package's page is read from the index in `[prepare.python]` (the simple API, as JSON or HTML). The wheel this interpreter prefers is chosen among the files whose hash the lock lists. Requests, the index's links and every redirect may reach only the index's origin and those in `hosts`; anything else is refused before it is sent, and no download starts until every file is known to be allowed. Each file is checked against the lock's hashes, then moved into a content-addressed cache, `deps/python/cache/files/<sha256>/<file>`, all at once. A broken or cancelled transfer leaves only a temporary file, which is never taken for an entry and is cleared at the next preparation. A broken transfer, a server error or a wrong hash is tried again, three times in all; an entry is hashed again each time it is used. The cache has a quota, `max_mb`. To make room, the entries used longest ago that this lock does not need are evicted; a lock that needs more than the quota is refused.
3. **The install.** `pip install --no-index --no-deps --require-hashes --no-build-isolation` runs in the sandbox, without network, from the cached files, mounted read-only. It gets only the sandbox's variables, never a model, endpoint or service credential, and it can write only the environment, its fork and private `/tmp`. It cannot write the project or your home. A wheel runs no code when it is installed. A package with no wheel for this interpreter is refused unless your config names it in `scripts`. Then its source distribution is built, and its build scripts run in the sandbox as the install does; its build backend must be in the lock, or be the package's own. An install that fails is not retried. The failure, with the end of pip's output, is recorded, and the environment is left unfinished. Commands never get it, and the next `molt env prepare` starts it over from nothing.

The environment is complete only once `molt-prepared.json` is written in it, last. That file lists the package manager, the lock's SHA-256, the interpreter, the index, each file with its URL, hash and size, and the packages built from source. A lock that was prepared before is not prepared again, and nothing is downloaded. Every preparation is appended to `deps/records.jsonl` under the data dir: when it ran, the workspace, `pip`, the lock's SHA-256, the environment, and `prepared`, `unchanged` or `failed`. A failure also has the step that failed (`lock`, `sandbox`, `venv`, `resolve`, `download` or `install`) and its error. Each record also lists the files, where each came from and whether it was downloaded or found in the cache, and the packages whose build scripts ran.

Once the lock is prepared, every run's commands, `molt env doctor` and the interface get its environment through the `python-prepared` profile. It mounts the environment read-only and puts its `bin` first on `PATH`, with `VIRTUAL_ENV` set. It comes before `python-venv`, so it wins over a `.venv` in the project. The readiness check says `requirements.txt (lock ...) is prepared`. When the lock changes, commands no longer get the old environment. The check is then `blocked`: it says the lock changed since it was prepared and to run `molt env prepare` again, which reuses every file already in the cache. A project never prepared has the dependency preflight's notice instead.

`[prepare.python]` goes in your user config, or a `--config` file. A project's `.molt/config.toml` cannot have a `[prepare]` section, so it can neither add an origin nor allow build scripts.

```toml
[prepare.python]
index = "https://pypi.org/simple/"            # the default
hosts = ["https://files.pythonhosted.org"]    # other origins files and redirects may come from; the default
scripts = ["pyyaml"]                          # packages that may be built from source, running their build scripts
max_mb = 2048                                 # the download cache's quota; the default
```

An index or origin with a user or password in its URL is refused, since Molt sends no credentials. The download honours `HTTPS_PROXY` and `NO_PROXY`. `--sandbox-policy` adds its read-only mounts, such as a Python outside `/usr`; its network and passed variables are not used.

Limits are inherited per process: address space, CPU time, file size, open files and process count, plus the existing command wall timeout. These are not aggregate cgroup quotas; RLIMIT_NPROC has the operating system's per-user semantics and does not limit root. TERM reaches the sandbox session group with 500 ms grace; KILL then tears down its PID namespace, including descendants that called setsid. Normal completion, cancelled handlers and service exit also tear down the namespace. Temporary mounts disappear with the last process. Future executable skills must use this shell path to share the policy.

### Commands at once, and a host that runs short

The shell service runs as many `shell.run` commands at once as the host has processors, and at least four; the rest wait their turn in the order they came, up to 64. Past that a command is refused at once, with an error that starts `the shell's queue is full:`. A command cancelled while it waits leaves the queue and never starts. `molt-tools shell --jobs N --queue N` changes both, in the shell service's `exec` args. Background processes (`shell.start`) are not counted.

A command the host cannot afford to start, because `fork` or the sandbox's namespaces failed for want of processes, open files, memory or namespaces, is started again after 100, 200, 400 and 800 ms, but only when it provably never started: the spawn failed, or bubblewrap failed before it created its namespaces. After the fifth try it is refused with an error that starts `short of host resources:`, names the resource and what bubblewrap or the OS said, and reports what the host has: this user's processes and threads, the process and open-file limits, the memory available, the cgroup's tasks and memory, and how many user namespaces are allowed. The sandbox's `processes` limit is an RLIMIT_NPROC, which counts every process and thread of the user, not only the command's; a busy host can exhaust it before the command starts. The planner reads such a check as out of resources, not a code failure, and starts no new attempt after it.

A host that cannot isolate commands (no user namespaces) or whose policy refuses to (a sysctl, AppArmor, a container's profile) gets an error that starts `isolation unavailable:`. Neither is tried again, and nothing runs unconfined instead. `molt env doctor` tells the three apart and says what to do for each. Molt reads the host's limits; it never changes them.

CI installs bubblewrap and requires namespace tests to run. A constrained local executor may skip only those integration tests after a failed capability probe; production startup still fails closed. Tests cover host paths, symlinks, read-only dependencies, network policy, host sockets, limits, C builds, cancellation and descendants with new sessions.
